# 미션 3·4·5 오류 수정 및 검증

2026-11-03 (Asia/Seoul) · 클라이언트 v89 · 네이티브/통신 호환 버전 `scene1`

## 미션 3: 엘리베이터가 바닥까지 내려오지 않음

기존 `2C65A` 사각형 검사 확장 코드가 1·2·3번 플레이어만 검사하고, 4·5번 비트는 그대로 다음 대상 선택 함수에 넘겼다. 엘리베이터 아래에 아무도 없어도 4번 플레이어가 장애물로 선택됐다. 전체 다섯 명에 같은 원본 사각형 검사를 적용했다. 실제 장애물이 있을 때의 정지, 화면 경계 제한과 이동/반전 루틴은 유지한다.

검증:
- 아무도 없는 경우: 수정 전 장애물 있음 → 수정 후 없음.
- 1~5번 각각 한 명만 내부에 있는 경우: 모두 해당 플레이어를 정확하게 선택.
- 네이티브 엘리베이터를 화면 안에 배치한 제어된 테스트: 수정 전 하강 위치 44에서 반전 → 수정 후 0까지 하강. 원본 상단 경계 184도 유지.

## 미션 4: 두 캐릭터를 한 사람이 같이 조작

사용자 진단 기록에서 2번 고정 플레이어 객체의 조작 소유 번호가 1이 아닌 0이었다. 두 객체가 같은 입력을 읽는 상태를 실제 코어의 애벌레 구간에서 재현했다.

고정 좌석의 활성 플레이어 객체에 한해, 조작 번호가 해당 좌석과 다르면 입력 처리 전에 복구한다. 연결 리스트에 없는 객체, 삭제된 객체, 적/연출 객체, 관전자, 퇴장자, 초기화 중인 RAM에는 적용하지 않는다. 시작과 부활 시 상태 객체에도 좌석 번호와 플레이어 포인터를 명시한다. 복구 이력은 오류 JSON의 `game.ownerRepairs`에 최대 20건 포함한다.

검증: 1번 오른쪽/2번 왼쪽 입력을 120프레임 적용했을 때, 정상 대조군의 X좌표는 `[224,28]`, 오류 상태는 `[224,220]`, 복구 적용은 `[224,28]`이었다. 다섯 좌석 각각의 소유 번호 복구와 정상 복구·제외 조건을 포함한 8개 단위 테스트도 통과했다.

**확인 범위:** 잘못된 소유 번호와 조작 공유의 인과관계, 복구 효과는 검증했다. 최초로 소유 번호를 덮어쓴 네이티브 명령은 확정하지 못했다. 이번 수정은 검증된 좌석 소유 관계를 보장하고 추가 원인 추적 정보를 남기는 방어적 수정이다. 위치를 강제로 벌리거나 캐릭터를 다시 생성하는 처리는 아니다.

## 미션 5: 여러 명 동시 납치 후 오류/중단

기존 3인 확장이 연출 인원 수를 3으로 만들었지만, 원본은 2일 때만 납치 대상과 남는 동료를 구분했다. 따라서 여러 연출 객체가 모두 납치 역할로 실행됐다. 4인 제어 테스트에서 기존 코드로 3명 동시 납치 후 프레임 2886에 초기화가 재현됐다.

수정:
- 활성 좌석 중 한 명만 납치 대상, 나머지는 원본의 동료 역할로 생성.
- 역할별 대기 신호를 좌석 0 여부 대신 납치/동료 구분에 연결.
- 생성 전 필요한 객체 여유분을 확인하여 부분 생성/재시도 중복을 방지.
- 연출 종료 이동 명령을 모든 활성 좌석에 명시적으로 전달.
- 진행 관리자의 활성 상태 검사 `42CAE`에 빠져 있던 4·5번 좌석을 추가. 4·5번만 남았을 때 출구 도달 후에도 다음 구간을 기다리던 오류를 함께 해결.

검증: 1~5인, 2·4번 두 명만 생존, 3번/4번/5번 각각 혼자 생존한 총 9개 조건에서 **납치 1명**, 나머지 인원의 동료 역할, 초기화 없음, 다음 구간(네이티브 substage 4) 진입을 확인했다.

## 검증 방식과 배포

실제 운영 코어와 네이티브 게임 코드를 로컬에서 실행했다. 시작 위치와 무적/보스 격파 시점을 제어해 재현 시간을 줄였다. 연출·이동·충돌·구간 전환은 원본 상태 머신을 실행했다. 전체 캠페인을 5대의 브라우저로 처음부터 끝까지 플레이한 결과를 의미하지 않는다.

재현 스크립트와 실행 방법은 `tests/ms3-scenes/README.md`, 요약 결과는 `docs/ms3-mission-3-4-5-verification.json`에 있다. 생성기는 `tools/ms3-build-scene-fixes.py`이며 원본 ROM 없이 동일 패치 바이트를 재생성한다. 원본 ROM, BIOS, 네이티브 스냅샷, 회원 진단 원문은 저장소에 넣지 않았다.

변경된 코드는 GitHub Pages 게임 클라이언트에서 로딩된다. Sites 게임 서버를 재배포할 필요는 없다. `scene1` 프로토콜은 이전 `hp1` 코어와의 방 내 혼용을 거부한다. 적용하려면 참가자 모두 게임 페이지를 새로고침하고 새 방에서 시작해야 한다. 이미 실행 중인 게임에는 강제로 적용하지 않는다.

추가 회귀 검사: 독립된 5인 코어 두 개의 4,000프레임 실행에서 22개 RAM/라이프사이클 비교와 체크포인트 복원이 일치했다. 기존 진단 저장·개인정보 제외 테스트도 통과했다.
