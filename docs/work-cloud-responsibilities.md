## 온라인게임 공개 전환 순서

1. work가 기존 Sites 서버에서 회원 식별을 유지하며 테스트 비밀번호 제한을 제거할 방법을 확인한다. 회원 ID·세션 헤더·엔드포인트·응답·차감 중복 방지 계약을 변경해야 한다면 먼저 이쪽에 전달한다.
2. work가 기존 클라이언트와 호환되는 서버를 먼저 배포하고, 회원 허용·비회원 거절·구매/정산 결과를 검증한다. 테스트 비밀번호를 공개 코드나 문서에 넣지 않는다.
3. 서버 준비 결과를 받은 뒤 이쪽이 최신 main에서 테스트 로그인 화면 제거를 적용하고 검증한 후 Pages를 배포한다.
4. work가 실제 계정으로 최종 확인한다. 실패하면 변경한 담당자가 해당 변경 범위만 되돌리고 결과를 전달한다.

주의: `codex/member-games-release`의 `25067bc`는 공개 클라이언트 후보였지만 현재 main의 조상이다. 그 뒤 `652ebad`에서 기존 테스트 로그인 흐름을 복원했다. 후보 브랜치를 단순 병합해도 공개 변경이 다시 적용되지 않는다. main을 과거 후보로 되돌리거나 전체 파일을 덮어쓰지 말고, 최신 main에서 필요한 클라이언트 변경만 새 커밋으로 적용한다.

## 인계와 동시 작업 규칙

- 서로 다른 담당 영역은 병행할 수 있다. 같은 파일·서비스·운영 시트에는 한 명만 쓴다.
- 담당을 바꿀 때는 기존 담당이 작업을 멈추고 마지막 커밋·미반영 변경·배포 상태를 전달한 뒤 새 담당이 이어받는다. 응답이 없다는 이유로 담당권을 넘겨받았다고 판단하지 않는다.
- 인계에는 작업 번호, 저장소/서비스와 파일 범위, 기준 커밋, 변경 커밋/브랜치, 검증 결과, 실제 배포 여부, 남은 작업을 포함한다. 운영 데이터 작업은 대상 월·실행 여부·백업 위치도 포함한다.
- 배포 직전에 최신 원격 커밋과 운영 상태를 다시 확인한다. 예상과 다르면 먼저 변경 내용을 대조한다. 강제 push와 과거 작업 폴더 전체 업로드로 덮어쓰지 않는다.
- 5번 보정은 work만 실행한다. 11월 전체 재집계·회원 상태 초기화와 혼합하지 않는다. 같은 원본을 양쪽에서 재입력하지 않는다.
- 이 문서는 조율 기준이며 다른 대화의 실행을 기술적으로 잠그는 장치는 아니다. work가 이 기준을 전달받고 따르는지 확인되어야 실제 충돌 방지 효과가 있다.

이 문서 자체는 별도 문서 브랜치에만 저장한다. 문서 작성으로 운영 Pages, Apps Script, Sites, 스프레드시트 또는 TURN 설정을 변경하지 않는다.
